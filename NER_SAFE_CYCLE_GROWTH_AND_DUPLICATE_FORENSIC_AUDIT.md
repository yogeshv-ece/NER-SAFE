## 4. Operational vs Test-Cycle Distinction & Prevention of Test Contamination

### Schema Deficiency Identification
Previously, `ProspectivePrediction`, `CNNEvidenceRecord`, and `C15EvidenceRecord` only recorded `cycle_id`, without an explicit field denoting execution origin. Consequently, if future outcomes were attached, the evaluator could not natively distinguish predictions generated by automated unit/integration test runs from operational live monitoring cycles.

### Architectural Enhancement Implemented
1. **Non-Destructive Schema Extension:** Added `cycle_origin: str = "OPERATIONAL_LIVE"` to:
   - `ProspectivePrediction`
   - `CNNEvidenceRecord`
   - `InSAREvidenceRecord`
   - `C15EvidenceRecord`
   - `AutonomousScheduler.__init__(..., cycle_origin="OPERATIONAL_LIVE")`
   - `record_live_monitoring_cycle(..., cycle_origin="OPERATIONAL_LIVE")`
2. **Evaluator Provenance Filter:** Enhanced `evaluate_prospective_performance()` with:
   - `filter_origin: Optional[str] = "OPERATIONAL_LIVE"`
   - Known test cycle exclusion set: `{"CYCLE-20260918061346-1", "CYCLE-20260918061435-1"}`.
   - For historical records where `cycle_origin` was omitted, the evaluator cross-references the known test cycle set and excludes test-generated predictions from operational metrics.
3. **No Destructive Rewriting:** Existing ledger records were **not** modified or rewritten. The provenance filter guarantees test data will never contaminate future operational model validation.
